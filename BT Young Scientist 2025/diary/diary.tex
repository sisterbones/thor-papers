	Started implementing caching in the MET Norway Locationforecast Provider. This is done using a class called \texttt{CachingWeatherProvider} that simply checks if there's a cache and if it expires.
	
	\begin{lstlisting}
# /thor/providers.py, commit a33720c, starts line 45
class CachingWeatherProvider(WeatherProvider):
	def __init__(self, lat: float, long: float):
		super().__init__(lat, long)
		
		self.last_fetched_time = 0
		self.seconds_to_live = 6000 # 10 minutes
		self.cached_response = {}
		
	def fetch(self) -> dict:
		if (time.time() > last_fetched_time + seconds_to_live):
			return cached_response
	\end{lstlisting}
	
	However, actually fetching the data is still the job of the specific Provider for MET Norway. This isn't ideal long term because I would have to implement the same code across every Provider that wants to make use of caching.

	\section{Week 6 and Week 7} % 14 Oct
	\begin{small}\begin{center}
			\textit{I forgot to keep a log of my progress over these weeks, so I have to merge them together.}
	\end{center}\end{small}

	Rewrote the display node code as the code I had written before was hard to expand. Created a class \texttt{EPaperImage} to represent an image, and another class \texttt{BodyStackItem} for alerts to be stacked on top of each other in the \texttt{EPaperImage}. The script checks how many alerts can be shown on screen at once (for the pHAT, it should be a maximum of 2) and then establishes a connection to the MQTT broker on the Hub. At the moment, the username, password and broker ip address are hardcoded, which makes it annoying to change.
	
	When a message is received, either a weather or an alert message, the script creates an image using the Pillow library and draws the information onto the image, before sending it to the display. 
	
	On the Hub, I added a database to store alerts in that uses SQLite, and created a class called \texttt{Alert} to represent an alert. I then derived from that another alert \texttt{LightningAlert} to quickly configure parameters on \texttt{Alert}. I also created a new Provider to fetch weather warnings from Met Éireann, and a new alert type to go with it. When the Hub is fetching alerts from the database, it checks if there's any weather warnings and includes them in the response if there are.

	\section{Week 10 and Week 11} % 11 Nov
		I wrote an autodiscovery script that works by listening to UDP packets from nodes, based off code I found on GitHub by user jholtmann, and added a new SystemD service for it. I also began work on an API to allow clients to set and retrieve settings stored in the database, as well as define an endpoint for nodes to self-register at. I also started looking into how to get around \texttt{FlaskMQTT}, the package I was using for MQTT support on the Hub, only supporting running on one process at a time (if I ran more than one instance of the hub for performance reasons the response over MQTT would be sent more than once). At this time, I simply disabled it in the Flask app factory config unless it was being enabled explicitly when it was run. I also started working on a universal installer for THOR, but I chose not to complete it to focus on other parts of the project. 
		
		I also started work on the Alerts program for my desktop. I was originally going to design it using the Qt GUI framework, but I ended up choosing wxFrames (which I would be accessing using the \texttt{wxPython} module) as it would be easier to create a system tray icon. The program connects to the Hub using Socket.IO rather than MQTT to avoid needing to do UDP autodiscovery and registration (this has the benefit of allowing the user to pick a Hub that isn't on the local network). At the moment, it only shows the current weather. 
		
		I had to create an icon set for this, called THORICONS, because not every icon set has all the icons I want and icons aren't consistent across different platforms anyway\footnote{Or even across the same platform. Windows 8's iconography is completely different from Windows 11's.}. To avoid having to draw an icon for a specific scenario, I designed a system where a script would draw different images on top of each other to create a single icon.
		
		\begin{lstlisting}
from PIL import Image
# /icongenerator/generate.py starting line 19, commit b955cd			
for icon in needed_icons:
	new_icon = Image.new("RGBA", (32, 32))
	
	# Split icon names into their different parts and load the images
	parts = icon.split("-")
	# Set variations of parts
	if 'rain' in parts:
		if {'rain', 'lightning'}.intersection(set(parts)):
			parts[parts.index('cloud')] = 'cloud_grey' # Grey clouds if raining
	if len(parts) <= 1:
		if 'sun' in parts: # Show a large sun if no other parts in image
			parts = ['sun_large']
		if 'moon' in parts:
			parts = ['moon_large']
	
	# Try load the icons
	for part in parts:
		if part not in image_parts:
			try:
				image_parts[part] = Image.open(os.path.join('img', f"{part}.png"))
			except FileNotFoundError:
				image_parts[part] = Image.new("RGBA", (32, 32))
			
			# Overlay the part onto the image
			new_icon.paste(image_parts[part], mask=image_parts[part])
	
	new_icon.save('../assets/icons/' + icon + '.png', 'PNG')
		\end{lstlisting}
		
		I drew the icons in a pixel art style using the software Aseprite, because I'm familiar with drawing pixel art and it is easy to do.

		\section{Week 12} % 2 Dec -- 8 Dec
		I began implementing UDP autodiscovery on the nodes, as before it was hardcoded. To do this, I created a simple way to read and write to a JSON file serving as a configuration file to save the server settings to avoid searching for a Hub every run. Then I broadcast a UDP packet to \texttt{255.255.255.255}\footnote{Which means every device on the network} and hit the node registration endpoint on the Hub that responds to get MQTT credentials. I added this to the display node and I began writing the lightning provider node. This is when I found out that the lightning sensor wouldn't talk to the Arduino Nano either, so I made the Arduino Uno send the data from the sensor to the Nano over a UART serial connection, which would then send it to the Hub over MQTT.
		
		On the Hub, I moved MQTT into its own Python module because having the Alerts app open was causing the Hub to freeze, so I needed to run more than one instance of it. The MQTT module (or bridge, I guess) sends MQTT messages to the Hub over the Hub's Socket.IO server, in a different 'namespace' to allow the Hub to know if the message is from MQTT. I also made the node registration API return the MQTT broker details, username and password.
		
		I also refactored the THOR Alerts app into a Python module to clean up the code base a little bit.
